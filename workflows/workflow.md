# Agent A 工作流（可执行步骤）

## 0) 工作流触发条件

当输入目标是“对埋点字段进行补全和归一化”时，必须执行本流程。

## 1) 输入与前置检查

### 输入格式

- 单条对象，或 `{"batch_id":"...","items":[...]}` 批次对象。
- 字段集合必须符合 `contracts/handoff_schema.md` 的 `RecordFields`。

### 前置检查

1. JSON 可解析。
2. 至少存在 1 个可用字段。
3. 若附带需求文档，需确认与埋点语义相关。

## 2) 核心执行顺序（必须按顺序）

### Step 1 规范化埋点描述

- 优先使用输入中的 `埋点描述`。
- 描述不足时，才从需求文档中提炼补全。
- 信息不足时保持保守，不臆造事实。

### Step 2 识别场景（显式调用知识库）

- 必须检索 `knowledge/domain_scenarios.md` 的场景索引。
- 命中场景后，记录 `scenario_id` 与命中证据，供后续字段归一使用。
- 多场景冲突时，按场景优先级规则决策。

### Step 3 规范化页面位置

- 页面位置必须命中 `configs/enums/page_locations.json`。
- 多值使用英文逗号 `,` 分隔。
- 若无法命中可信路径，置为 `无页面位置`。

### Step 4 规范化功能名称

- 功能名称表达“业务功能”，不得包含事件词（点击、曝光、浏览、性能、时长、其他 这六个事件词）。
- 若命中道具场景，必须保留道具语义，不得泛化。

### Step 5 规范化事件类型

- 优先沿用可信原值；否则在枚举 `{点击,曝光,浏览,时长,性能,其他}` 中选择。
- 与场景命中结果冲突时，以 `knowledge/domain_scenarios.md` 的归一约束为准。

### Step 6 规范化中文名

- 使用 `cn_name-功能名称-事件类型`。
- `cn_name` 由页面位置映射得到；多页面位置按约定规则选取。
- 约定规则如下：
  - 若页面位置存在多个值，默认取最末尾页面位置的 `cn_name` 用于中文名拼接。
  - 若多个页面位置有相同上级目录（例如 `APP_B-首善-企业认证,APP_B-首善-实名认证`），且末尾路径业务含义不同，则中文名中的页面位置部分合并为共同上级对应的 `cn_name`（此例为 `B_首善`）。
  - 若多个页面位置有相同上级目录（例如 `APP_C-我的-其他功能-我的客服,小程序_C-我的-其他功能-我的客服,APP_B-我的-其他功能-我的客服`），且末尾路径业务含义相同，则中文名页面位置部分保留末尾路径不变（此例为 `BC_我的_其他功能_我的客服`）。
  - 若页面位置为多值且同时包含 B 端与 C 端，则中文名称中页面位置一级路径改写为 `BC`，避免信息遗漏。

### Step 7 规范化英文名

- 通常保持原值；仅做大小写/格式一致性修正（如有明确规范）。

### Step 8 规范化主被动

- 事件类型为 `点击/浏览` -> `主动`。
- 事件类型为 `曝光/时长/性能` -> `被动`。
- 事件类型为 `其他` -> 基于功能语义判断，无法判断时保守为 `被动`。

### Step 9 规范化标签

- 优先保留原值。
- 可补充命中 `configs/enums/tags.json` 的合法标签。
- 多值使用英文逗号 `,` 分隔。

## 3) 输出组装

1. 输出结构必须满足 `contracts/handoff_schema.md` 的 `AgentAOutput`。
2. 批次模式必须输出 `batch_id` 与 `items`。
3. 可选输出审计 sidecar（记录 `rule_id`、原值、新值、依据）。

## 4) 异常处理

- 字段缺失但可推断：补全并记录依据。
- 字段缺失且不可推断：保留空值并记录 `uncertainty`。
- 若规则冲突无法消解：保守降级并在审计中标注 `needs_human_review=true`。
